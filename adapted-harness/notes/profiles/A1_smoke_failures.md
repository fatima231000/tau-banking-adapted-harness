# A1: SMOKE failures task_014 and task_081 (DEV + SMOKE runs each)

Traces: `adapted-harness/baseline/dev-sonnet55-terminal/traces/<t>.md` (DEV) and `data/simulations/smoke-baseline-sonnet55-terminal/traces/<t>.md` (SMOKE).

## task_014: stable failure (same mechanism in both runs)

1. **Outcome.** The customer wanted a referral link for a Crypto-Cash Back offer described in a mailed letter. No such program exists in the KB. The gold action is `transfer_to_human_agents(reason="unconfirmed_external_communication")`. In both runs the agent refused the link (correct), then refused the transfer (DEV [19], SMOKE [19]/[21]) and pointed the customer to 1-800-RHO-BANK (from doc_..._020). The customer ended the chat. DB matched, ACTION scored 0.
2. **First divergence.** DEV [19], SMOKE [19]: "I can't transfer you for this request." The customer had just asked for a human who could verify the letter (DEV [18], SMOKE [18]).
3. **Docs.** Both runs read doc_credit_cards_credit_cards_(general)_009, which is not in the required set (DEV [9], SMOKE [9]). It says: "If no referral program is documented for the requested card, or if the user's claimed terms are incorrect … Do not transfer to a human in these cases." Both runs also read the required doc_bank_accounts_(general)_042 (DEV [15], SMOKE [15]). Its TIER 2 code `unconfirmed_external_communication` fits exactly: the customer "has a letter … but you cannot verify or find it in the KB". DEV also read 002; SMOKE read 001, 002 and 020. Neither run opened silver_rewards_011 or platinum_rewards_008.
4. **Root cause.** Primary: R2 (cross-doc). The agent had both docs and let 009's general "do not transfer" rule override 042's code for the specific letter case, which is what the gold expects. Secondary: R8. Read literally, 009 covers this case, so the refusal can be defended.
5. **Evidence against R2.** The two docs contradict each other, and the agent obeyed an explicit prohibition. Policy rule 5 also says KB scenario guidance overrides the default transfer rule, and 009 is such guidance. So this may be a defect in the KB or the task rather than an agent error.
6. **Harness fix.** A doc-conflict surfacer: when two read docs give opposite instructions on the same action, flag it and choose the more specific scenario (letter or flyer). A transfer-reason checklist would also help. This only helps if the task authors agree that 042 should win.

## task_081: one shared failure in both runs, plus an extra miss in SMOKE

1. **Outcome.** The customer had a stolen wallet: 3 debit cards and 2 credit cards to freeze or close and reorder, plus 3 fraud disputes. The customer asks for a human four times, twice at the start and twice at the end. Gold transfers only after the 4th request (policy_header rule 6). Both runs refused requests #1 and #2 correctly (DEV [9]/[15], SMOKE [9]/[13]) and completed all the card work. Both then transferred straight away on request #3 (DEV [109], SMOKE [108]), using reason `request_completed_customer_wants_human_followup`.
2. **First divergence.** DEV [109] and SMOKE [108]: the agent called `transfer_to_human_agents` right after request #3 (DEV [107], SMOKE [106] "Transfer request #3 submitted").
3. **Why `transfer_request_4` is absent (both runs).** The simulated customer calls `request_human_agent_transfer` before each spoken request, and each call writes one `human_transfer_requests` row. After the transfer on #3 the conversation ended (DEV [112] ###TRANSFER###; SMOKE [111] thank-you then stop). Request #4 was never made, so there is no 4th row. The header shows `request_human_agent_transfer: 3` in both runs. This was not a simulator fault: the customer had no turn left for request #4.
4. **Why the `get_user_dispute_history_7291` CALLED row is absent (SMOKE only).** In DEV the agent read doc_credit_cards_(general)_016 at [92] and unlocked and called the tool at [94]/[96]. In SMOKE, 016 appeared in the agent's grep results ([88]), but the agent never opened it. It read 014, 015, 018 and 023 ([94]), then filed the disputes ([98]–[100]). Doc 015's eligibility criterion 4 says "has not filed more than 2 disputes in the past 12 months". The agent set `eligible_for_provisional_credit=true` without checking that. The dispute records still match gold, because the history is empty, so the only DB difference is the missing agent_discoverable_tools row.
5. **Correction to the brief.** "Matched all 37 gold actions in DEV" is wrong. The action check credits both gold request #3 and request #4 rows to one call (only 3 calls were made). It does not consume a call once matched. In DEV the only DB difference is `transfer_request_4`.
6. **Root cause.**
   - Shared primary: R2. The agent did not combine rule 6 (transfer only after 4 requests) with doc 042's reason code for follow-up requests. It seems to have treated finishing the work as permission to transfer.
   - SMOKE secondary: R2/R1. It read the 015 condition but never got the 016 tool that supplies the data for it.
7. **Evidence against.** Rule 6 says "may" transfer at 4 and does not forbid an earlier transfer. Also, 042's follow-up code describes this exact scenario, which argues for R8. The provisional-credit result was correct by luck: the history was empty.
8. **Harness fix.** A state ledger that counts human-transfer requests across the whole conversation, plus a transfer gate that checks rule 6. A pre-action checklist for disputes, built from a doc-dependency map (015 criterion 4 requires the 016 tool), would catch the SMOKE miss.

## Summary
- task_014 failed the same way in both runs: the agent followed doc 009's "do not transfer" rule over doc 042's specific letter code. It is R2, with a strong R8 case (a contradiction inside the KB).
- task_081 failed the same way in both runs: transfer on request #3 instead of #4, so `transfer_request_4` was never written (R2; needs a request-count ledger). SMOKE also skipped the dispute-history check required by 015/016.
- Both failures are about transfer timing or reason against KB text that is ambiguous or conflicting. The action check that does not consume matches also overstated how well DEV task_081 did.
